# Dataset card: second machine, Intel Core i5-13500 under WSL2

Timing measurements of the four programs of this repository (sequential, OpenMP, Pthreads, MPI) for merge sort and dense matrix
multiplication on a desktop computer, taken with the same harness (`benchmark/run_benchmark.py`) as the laptop dataset in
[`benchmark/results/`](../results/). **1088 recorded runs in 128 configurations, 5 measurement sessions, worker counts 1, 2, 4, 8 and 16.**
Every run exited with status 0 and printed exactly the same output as the sequential program for the same input (SHA-256 comparison).

- Dataset DOI: [10.5281/zenodo.24554982](https://doi.org/10.5281/zenodo.24554982) (Zenodo). The same data with a combined two-machine table is on Hugging Face:
  [Namra-5/hpc-parallel-matrix-sorting-benchmark](https://huggingface.co/datasets/Namra-5/hpc-parallel-matrix-sorting-benchmark).
- Licence: CC BY 4.0 for the data; MIT for the code.
- The README section that summarises these results is generated by [`benchmark/machines_table.py`](../machines_table.py).

## Files

Each session has its own sub-folder (`uni_s1a` to `uni_s3a`); the sessions measure different sizes and are never merged by hand.

| File (per session) | Content |
|---|---|
| `raw_runs.csv` | One row per recorded run: timings, execution order, start time, load, exit code, output hash, status |
| `benchmark_results.csv` | One row per configuration: medians, spread, speedups, efficiencies, `scaling_valid` (same columns as the laptop dataset) |
| `hardware_environment.json` | Hardware, software, code commit and the measurement protocol of the session |
| `inputs_manifest.json` | SHA-256 of every input file used |
| `lscpu_full.txt`, `cpu_model.txt`, `run.log` | `lscpu` output and CPU model as seen inside WSL2; the complete harness log |
| `*.png` | Figures made by `benchmark/plot_results.py` |

`progress.txt` (in this folder) is the driver log of the unattended run: every session start, end, restart and snapshot with UTC
times. `SHA256SUMS` lists the checksum of every file here (`sha256sum -c SHA256SUMS`). Line endings of the CSV files must not be
converted; `.gitattributes` marks this folder `-text` for that reason.

## Validation

A run is `ok` only if the process exited with status 0 and its output hash equals that of the sequential run on the same input;
`machines_table.py` refuses to produce the README section unless every run is `ok`, each session has exactly the number of runs its
protocol implies, sessions do not share a (workload, size) and all sessions come from the same CPU. For this release:
`benchmark/standardize.py`, applied again to each `raw_runs.csv`, reproduces `benchmark_results.csv` exactly (maximum difference 0.0), and the
speedup `S_N` (kernel median with 1 worker divided by kernel median with N workers, same model) was recomputed from the raw runs with separate
code and agrees with the stored `kernel_speedup_vs_1worker` to within 5e-7. 104 of the 128 configurations have `scaling_valid = true`
(at most 10 workers, the cores the harness counted); the others are kept but flagged `oversubscribed`.

## Limits of these data

- **Hybrid CPU, topology hidden by WSL2.** The processor is an Intel Core i5-13500, which Intel specifies as 14 cores
  (6 performance cores with hyper-threading and 8 efficiency cores) and 20 threads. Inside WSL2, `lscpu` reported 10 cores x 2
  threads, so the harness used 10 as the number of usable physical cores. That figure is a property of the virtual machine,
  not of the chip.
- **Placement is not observable.** Which Windows logical processor runs which worker is decided by the host scheduler and was
  not recorded. Runs with more than 6 workers may therefore mix performance and efficiency cores or hyper-thread siblings.
  `scaling_valid` follows the harness figure of 10 cores and is **not** evidence of 10 identical cores; the cleanest scaling
  data are the 1-, 2- and 4-worker points.
- Worker counts above 10 are flagged `oversubscribed` by the harness even where they do not exceed the 14 physical cores of the chip.
- Virtualised (WSL2 on Windows): timer, scheduler and memory behaviour can differ from bare metal; the CPU governor was not
  observable. Host (Windows) load is not visible from inside WSL2.
- **Collected on two days, in five sessions, after two unplanned shutdowns.** Sessions `session_1` to `session_4` were measured on
  2026-11-24 and `session_5` (matrix 4000) on 2026-11-26. On 2026-11-24 the machine was shut down twice while a session was
  running (the sessions with sorts and with matrix 3000); the cause was not recorded. The interrupted sessions were discarded and
  measured again from the start; their partial data are not part of this dataset. The driver log `progress.txt` in `machines/<machine_id>/`
  records every start, end and restart.
- **Single-core speed was not clearly higher than that of the older laptop in the same dataset.** Median sequential kernel time,
  PC against laptop, at the five (workload, size) pairs measured on both: matrix 1000 2.80 s against 2.53 s (PC 11% slower),
  matrix 1500 10.1 s against 17.5 s (PC faster), sort of 50,000 elements 4.2 ms against 4.8 ms (PC 11% faster), sort of 500,000
  0.051 s against 0.049 s (PC 5% slower), sort of 5,000,000 0.554 s against 0.517 s (PC 7% slower). The cause was not identified.
  Windows power mode, CPU frequency and whether the WSL process ran in an efficiency mode were not recorded. Absolute times therefore
  describe this environment, not the processor's capability; speedups compare runs inside the same session.
  The laptop dataset was collected in the best-performance power mode (stated in its provenance); the power mode of this machine was
  not recorded, so the two datasets may differ in this respect.
- **Repetition counts differ by size.** Matrix 1000 to 3000 have 5 repetitions per configuration, sorts 15, and matrix 4000 only 3
  (one session took about 3.9 hours), so matrix 4000 has no speedup interval. One-worker runs at matrix 4000 vary by about
  +/-12% between repetitions (sequential 446 to 565 s), and at matrix 3000 the sequential program is about 9% slower in repetitions 4 and 5 than in repetitions 1 to 3.
- Matrix 5000 and the 20,000,000-element sort were not measured.

Further general limits are as for the laptop dataset: one input instance per size, one input distribution, MPI on a single node over
shared memory, and a virtualised environment (WSL2) whose timer, scheduler and memory behaviour can differ from bare metal.
