# Dataset card: parallel merge sort and matrix multiplication scaling measurements

Validated timing measurements of four execution models (Sequential, OpenMP, Pthreads, MPI) on two workloads (merge sort and
dense matrix multiplication), produced with the tooling in this repository. Every recorded run exited with status 0 and printed
exactly the same output as the sequential program for the same input.

## Files

| File | Content |
|---|---|
| `raw_runs.csv` | One row per recorded run (780 rows): timings, execution order, start time, machine load, exit code, output hash, validation status |
| `benchmark_results.csv` | One row per configuration (78 rows): medians, spread, speedups, efficiencies, `scaling_valid` |
| `hardware_environment.json` | Machine, OS, compiler, MPI, flags, seed, measurement protocol and code version |
| `inputs_manifest.json` | Size and SHA-256 of every generated input file |
| `lscpu_excerpt.txt` | Raw `lscpu` lines (model, cache sizes, virtualisation) from the measurement machine |
| `python_packages.txt` | Versions of pandas, numpy, matplotlib and pytest used for the analysis step |
| `*_speedup_kernel.png`, `*_speedup_wall.png`, `*_kernel_time.png`, `*_kernel_time_all_workers.png` | Figures drawn from the CSVs (one set per workload) |
| `SHA256SUMS` | Checksums of the data and figure files (`sha256sum -c SHA256SUMS`) |

Column and field definitions, the measurement protocol and the timed region of each program:
[`../README_BENCHMARK.md`](../README_BENCHMARK.md).

## Provenance

- Collected 2026-11-15 (UTC) on one laptop: Intel Core i5-7200U (2 physical cores, 4 hardware threads), 3.77 GiB RAM, WSL2
  Ubuntu 24.04 on Windows, gcc 13.3.0, Open MPI 4.1.6, Python 3.13.12; plugged in, best-performance power mode, idle.
- Code version: git commit `411d64e74780f530864ea7cbbd7cef4d4e59e78b`. The C sources, Makefiles and `run_benchmark.py` are unchanged
  in later commits (later changes affect only the analysis scripts, tests and documentation); check with
  `git diff 411d64e -- common merge_sort/src matrix_multiplication/src merge_sort/Makefile matrix_multiplication/Makefile benchmark/run_benchmark.py`.
- Command:

```bash
python3 benchmark/run_benchmark.py --workload both \
    --matrix-sizes 500 1000 1500 --sort-sizes 50000 500000 5000000 \
    --workers 1 2 3 4 --reps 5 --sort-reps 15 --cooldown 20 --warmup \
    --notes "WSL2 Ubuntu 24.04 on Windows, 2 cores/4 threads laptop, plugged in, best-performance mode, idle"
python3 benchmark/standardize.py
python3 benchmark/plot_results.py
```

- Design: matrices 3 sizes × 13 configurations (sequential, and OpenMP / Pthreads / MPI with 1–4 workers) × 5 repetitions
  = 195 runs; merge sort 3 sizes × 13 configurations × 15 repetitions = 585 runs; 780 recorded runs in total.
  Per input there is one additional untimed sequential reference run, and a warm-up run precedes every repetition; neither is
  recorded. The order of the configurations is shuffled inside every repetition with a fixed seed and stored in `order`; a
  20 s cooldown separates repetitions.
- Inputs are generated from a fixed seed (`data_seed` 20260101). Merge sort: integers uniform in [1, 10000]. Matrices: two n×n
  matrices of doubles uniform in [0, 9999). The input files are not included; regenerating them with the same command gives files
  whose SHA-256 should match `inputs_manifest.json`. This was verified on a second machine with a different Python version
  (3.12; the measurement used 3.13): all nine input files were regenerated with identical SHA-256 hashes.

## Validation rules

A run is `ok` only if the process exited with 0 **and** the SHA-256 of its standard output equals that of the sequential program
on the same input. Only `ok` runs are aggregated. The README results block is generated by `benchmark/results_table.py`,
which refuses to state that all runs are validated unless every recorded run is `ok` and the number of runs equals what the
recorded protocol implies. Every statistic in `benchmark_results.csv` was also recomputed independently from `raw_runs.csv`
with separate code and agreed to 5×10⁻⁷ (the rounding of the stored values). `scaling_valid` is true for configurations with workers ≤ the 2 physical cores; the 36 configurations
with 3 or 4 workers are oversubscribed and kept for completeness but excluded from scaling claims (42 configurations remain).

## Intended use and limits

Intended for comparing parallelisation strategies and studying measurement validity. It is **not** a hardware benchmark: the
matrix kernel keeps a cache-unfriendly textbook loop order, and absolute times are far slower than a tuned library.

Threats to validity:

- **One machine, two physical cores.** Valid scaling covers 1 → 2 workers only; nothing is known about more cores or other CPUs.
- **Virtualised environment (WSL2).** Timer, scheduler and memory behaviour can differ from bare metal; the CPU governor and
  frequency are not observable (`cpu_governor` is null).
- **Timing noise is right-skewed.** Occasional slow repetitions (background activity on the host) inflate the coefficient of
  variation; medians are reported with min, max, standard deviation and `kernel_cv`, and every repetition is in `raw_runs.csv`.
- **Millisecond-scale kernels (the 50,000-element sort) are the most sensitive** to CPU power state and scheduling; the
  randomised order, warm-up and 15 repetitions mitigate this but do not eliminate it.
- **One input instance per size and one input distribution.** Variation across different random inputs and data patterns
  (already sorted, reversed, …) was not measured.
- **Wall time includes serial text parsing and printing**, and for MPI the launcher start-up and output forwarding; `kernel_s`
  excludes them. MPI ran on a single node over shared memory, so network costs are not measured.
- **Hyper-thread configurations** (3 and 4 workers) are reported for completeness; their behaviour is not explained here.
